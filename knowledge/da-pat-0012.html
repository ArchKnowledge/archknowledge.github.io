Pattern · Master Data

Master Data Hub

Manage shared master data entities in a hub that performs identity resolution, maintains golden records and cross-references, and distributes master data, in registry, consolidation, coexistence or centralized style.

Draft knowledge. Status proposed, quality draft. Not yet reviewed or approved by a human architect.

Problem

The same business entity exists in many systems with conflicting values and identifiers.

Context

Customer, product or supplier data maintained in several applications.

Forces

  • Source system autonomy vs. central authority.
  • Real-time consistency vs. implementation effort.

Solution

A hub matches records, keeps cross-references, applies survivorship to build a Golden Record and distributes it. Four common implementation styles:

Style Authoring Golden record Invasiveness
Registry in sources virtual (index + cross-ref) low
Consolidation in sources physical, read-only in hub (for analytics) low–medium
Coexistence in sources and hub physical, synchronised back medium–high
Centralized (transaction) in hub only physical, authoritative high

Architecture

Sources ⇄ match/merge + survivorship + cross-reference ⇄ Hub ⇄ distribution (API/events) → consumers

Advantages

  • Single identity; consistent attributes; reusable services.

Disadvantages

  • Organisational change; hub becomes critical infrastructure.

Risks

  • Technology-first MDM without ownership and definitions fails.

When to Use

  • Shared entities with material cost of inconsistency.

When Not to Use

  • Entities used by one system only.

Alternatives

Per-attribute authoritative sources with plain integration; Reference Data Hub for code lists.

Examples

  • Consolidation-style customer hub feeding the analytics platform, later evolving to coexistence.
