Pattern · Semantic Architecture

Concept-to-Model Traceability

Link every model element at each layer to the governed concept it represents and to the model element it realizes, so meaning and impact can be traced across layers.

Draft knowledge. Status proposed, quality draft. Not yet reviewed or approved by a human architect.

Problem

Nobody can tell which business concept a table or column represents, or which models are affected when a definition changes.

Context

Organisations with governed business concepts and models at multiple layers.

Forces

  • Traceability value vs. maintenance effort.

Solution

Maintain explicit links: physical column → realizes → logical attribute → realizes → information attribute → represents → concept. Store the links as metadata (e.g. concept IRIs in model annotations) and validate them automatically.

Architecture

Concept (semantic) ◀─represents─ Information element ◀─realizes─ Logical element ◀─realizes─ Physical element

Advantages

  • Impact analysis of definition changes; shared meaning in integration and migration.

Disadvantages

  • Needs tooling and discipline.

Risks

  • Links created mechanically without semantic review.

When to Use

  • Governed, shared or regulated data.

When Not to Use

  • Throw-away prototypes.

Alternatives

Glossary-only linking (catalog term to column) — weaker, skips intermediate layers.

Examples

  • Column klant.ingangsdatum linked to concept "Customer Since Date" through the information model.
