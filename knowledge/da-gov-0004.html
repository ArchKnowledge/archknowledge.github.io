Governance Lifecycle

The lifecycle states of governed artifacts and knowledge objects, the allowed and invalid transitions, and who may perform each transition.

Draft knowledge. Status proposed, quality draft. Not yet reviewed or approved by a human architect.

Purpose

Define the states a governed artifact (knowledge object, definition, model, decision) moves through, and which transitions are allowed. Machine-readable in 00-system/governance/lifecycle.yaml; enforced by dakb.py validate --base <ref>.

Scope

All objects in this repository; reusable for data definitions and models.

States

draft ─▶ proposed ─▶ under-review ─▶ validated ─▶ approved ─▶ published ─▶ implemented*
  ▲          │            │  │            │                     │   │           │
  └──────────┘            │  └▶ rejected ◀┘                     │   ▼           ▼
  ▲  (withdraw/rework)    │        │                            │ deprecated ─▶ retired
  └───────────────────────┘◀───────┘            (revision) under-review ◀┘
* implemented: decision-type objects only
State Meaning Who sets it
draft being authored author
proposed submitted for governance; maximum state an LLM may set author / LLM
under-review reviewer assigned and reviewing domain owner
validated review and automated validation passed reviewer
approved approved by role with decision rights approver (Decision Rights Model Architect)
published released in a knowledge product/release publisher
implemented decision realized in architecture owner, with evidence
deprecated no longer recommended approver
retired withdrawn, kept for traceability approver
rejected not accepted reviewer / approver

Allowed Transitions

draft→proposed, proposed→draft, proposed→under-review, under-review→proposed, under-review→validated, under-review→draft, under-review→rejected, validated→approved, validated→under-review, validated→rejected, approved→published, approved→deprecated, published→implemented, published→under-review (revision, requires explicit approval), published→deprecated, implemented→deprecated, deprecated→retired, rejected→draft.

Invalid Transitions (examples)

Transition Why invalid
draft → approved skips review and validation
proposed → published generation is not approval
validated → published validation is not approval
deprecated → published reinstatement requires a new review
retired → anything terminal; create a superseding object
any → implemented (non-decision) only decisions are implemented

Approval Requires a Governance Record

A transition into approved, published, implemented, deprecated or retired is valid only together with a governance record for the object's current version (Status Change Requires Governance Record). Editing the status field alone is rejected by validation.

Change Statuses Are Not the Same

For changes, the Architecture Change Process Architect distinguishes: change proposed ≠ technically valid ≠ architecturally valid ≠ governance approved ≠ implemented.
