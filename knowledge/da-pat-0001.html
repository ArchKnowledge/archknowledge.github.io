Pattern · Data Modeling

Bitemporal Data Model

Record both valid time and transaction time for each fact so that any past state can be reconstructed as it was true and as it was known.

Draft knowledge. Status proposed, quality draft. Not yet reviewed or approved by a human architect.

Problem

The business must answer "what was true at time T?" and "what did we believe at time T′ about time T?" — for example after retroactive corrections.

Context

Regulated domains (insurance, finance, public registers, HR/payroll) where corrections are backdated and decisions must be reproducible.

Forces

  • Retroactive corrections must not destroy what was previously known.
  • Queries must stay understandable.
  • Storage and write complexity grow with two time dimensions.

Solution

Every versioned fact carries two periods: a valid-time period [valid_from, valid_to) maintained by the application, and a transaction-time period [recorded_from, recorded_to) maintained by the system. Updates never overwrite: they close the current transaction-time period and insert new rows.

Architecture

Entity key | attributes | valid_from | valid_to | recorded_from | recorded_to

Queries filter on both periods ("as of valid date V, as known at T"). The information model states which entities/attributes are bitemporal; the physical model may combine an application-time period with a System-Versioned History Table.

Advantages

  • Full reproducibility of past decisions and reports.
  • Clean handling of backdated corrections.

Disadvantages

  • Complex writes (period splitting) and queries.
  • Higher storage.
  • Many tools and developers are unfamiliar with it.

Risks

  • Incorrect period maintenance creates gaps or overlaps; needs constraints and tests.
  • Uniform application to all entities over-engineers the model.

When to Use

  • Retroactive changes are common and reproducibility of past knowledge is required.

When Not to Use

  • Only an audit of changes is required → System-Versioned History Table or audit log.
  • Only analytical history of attribute changes → Slowly Changing Dimension Type 2.

Alternatives

System-Versioned History Table, Event Sourcing, Slowly Changing Dimension Type 2.

Examples

  • A policy premium is corrected in March with effect from January; the January invoice run can still be reproduced as it was.
