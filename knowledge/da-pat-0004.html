Pattern · Data Modeling

Event Sourcing

Persist every state change as an immutable domain event in an append-only log and derive current and past states by replaying events.

Draft knowledge. Status proposed, quality draft. Not yet reviewed or approved by a human architect.

Problem

The reason and sequence of changes matter, not just resulting states; state must be reconstructable and changes shared with other systems.

Context

Domain-driven systems with rich business events; audit-heavy processes.

Forces

  • Complete audit and replay versus query simplicity.
  • Event schema evolution over long periods.

Solution

Store each change as an immutable event (e.g. AddressChanged) in an append-only store. Current state is a projection built by replaying events; other projections serve queries and other systems.

Architecture

Command → Aggregate → Event Store (append-only) → Projections (read models) → Consumers

Advantages

  • Full history with intent.
  • Natural integration via events.
  • New read models can be derived retroactively.

Disadvantages

  • Querying current state requires projections.
  • Event versioning and replay complexity.

Risks

  • Events designed as CRUD deltas lose business meaning.
  • Personal data in immutable logs complicates erasure obligations (GDPR).

When to Use

  • Business events are first-class; audit with intent is required.

When Not to Use

  • Simple CRUD applications; teams without event modeling experience.

Alternatives

System-Versioned History Table, Bitemporal Data Model, Change Data Capture (for integration only).

Examples

  • A registration system storing VehicleRegistered, OwnerChanged, RegistrationSuspended.
