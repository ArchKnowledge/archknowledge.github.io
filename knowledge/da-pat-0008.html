Pattern · Data Integration

Data Contract

Make the interface between a data producer and its consumers an explicit, versioned, owned agreement covering schema, semantics, quality and service levels, and enforce it automatically.

Draft knowledge. Status proposed, quality draft. Not yet reviewed or approved by a human architect.

Problem

Consumers depend on data whose structure and meaning the producer changes without notice.

Context

Multiple teams producing and consuming data (data mesh, microservices, platforms).

Forces

  • Producer autonomy vs. consumer stability.
  • Formality vs. speed.

Solution

Define per data interface a contract: schema, semantics (links to concepts), quality rules, freshness/SLA, owner, version and change policy. Validate it in the producer's pipeline and at ingestion (Data Quality Gate).

Architecture

Producer ─publishes→ dataset + contract(vN) ─validated by→ CI & ingestion gate ─consumed by→ consumers

Advantages

  • Breaking changes become visible and negotiated.
  • Quality ownership sits with the producer.

Disadvantages

  • Governance overhead; contract sprawl.

Risks

  • Contracts that cover schema only, not meaning, give false assurance.

When to Use

  • Cross-team data interfaces with several consumers.

When Not to Use

  • Single-team, single-consumer pipelines.

Alternatives

Schema registry only (weaker), shared canonical model.

Examples

  • A "Policy Issued" dataset contract with fields, definitions, completeness ≥ 99.9% and 1-hour freshness.
