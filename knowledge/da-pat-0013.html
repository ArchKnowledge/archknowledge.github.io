Pattern · Reference Data

Reference Data Hub

Maintain code lists centrally with versions, validity periods and cross-list mappings, and distribute them to consuming systems.

Draft knowledge. Status proposed, quality draft. Not yet reviewed or approved by a human architect.

Problem

Code lists are copied into every application and drift apart.

Context

Many systems using the same classifications (status codes, product types, external code lists).

Forces

  • Local extensions vs. central consistency.

Solution

One governed store per code list with: code, label(s), definition, validity period, version, mapping to other lists and to vocabulary concepts. Distribution via API, files or events; consumers validate against it.

Architecture

Steward → Reference Data Hub (versions, mappings) → publish → systems / platform / catalog

Advantages

  • Consistent classification; controlled change.

Disadvantages

  • Additional component; synchronisation latency.

Risks

  • Retiring a code without validity periods breaks historical data.

When to Use

  • Code lists shared by several systems or used in regulatory reporting.

When Not to Use

  • Truly local, application-internal enumerations.

Alternatives

Master Data Hub (if the tool covers reference data), static published files.

Examples

  • Claim status codes with mapping to a regulator's reporting codes.
