Pattern · Data Integration

Change Data Capture

Detect inserts, updates and deletes in a source database (typically from its transaction log) and propagate them as a change stream to targets.

Draft knowledge. Status proposed, quality draft. Not yet reviewed or approved by a human architect.

Problem

Targets need source changes with low latency, without heavy load on the source and without modifying the source application.

Context

Replication to warehouses/lakes, cache invalidation, phased migrations.

Forces

  • Low latency vs. source impact.
  • Technical change events vs. business meaning.

Solution

Read the database transaction log (or triggers/timestamps as weaker variants), emit ordered change events per row, and apply them to targets.

Architecture

Source DB log → CDC connector → change stream (topic/queue) → target appliers / consumers

Advantages

  • Near-real-time; low source impact (log-based).
  • Captures deletes (log-based).

Disadvantages

  • Exposes the source's physical schema as an implicit contract.
  • Row-level changes lack business intent.

Risks

  • Source schema changes break consumers → mitigate with a Data Contract.
  • Log retention and connector outages cause gaps; needs reconciliation.

When to Use

  • Low-latency replication; Phased Data Migration synchronization.

When Not to Use

  • Consumers need business events → Event Sourcing / domain events.
  • Daily latency suffices → Batch Extract-Transform-Load.

Alternatives

Batch Extract-Transform-Load, Event Sourcing, Data Virtualization.

Examples

  • Streaming CRM customer changes into a lakehouse bronze layer (Layered Data Refinement).
