Database History Pattern Decision Tree

Guides the choice of a history mechanism from explicit reconstruction requirements.

Draft knowledge. Status proposed, quality draft. Not yet reviewed or approved by a human architect.

Purpose

Select a history pattern for a data set. Input: the information-level history requirement (Historical Requirements Are Explicit). Output: patterns to evaluate in Select Historical Data Strategy Professional.

Entry Question

Q1. Do you need to reconstruct historical states of this data?

Decision Logic

Machine-readable in decision_logic (front matter); run it with python 00-system/validation/dakb.py decide "Database History Pattern Decision Tree". The rendering below is generated by dakb.py index.

  • q1. Must historical states of this data be reconstructable? history.required
    • YES →
      • q2. Is history needed only for analytical reporting on descriptive attributes? history.analytical_attributes_only
        • YES → Analytical attribute history: Slowly Changing Dimension Type 2
        • NO →
          • q3. Is historical data queried operationally (by applications or users of the operational system)? history.operational_queries
            • YES →
              • q4. Must backdated business corrections be reconstructable 'as known at' a past time? history.retroactive_corrections
                • YES → Bitemporal history (transaction time may be realized by system versioning): Bitemporal Data Model, System-Versioned History Table
                • NO → Recorded-state history: System-Versioned History Table
            • NO →
              • q5. Is the reason or intent of each change required (audit with business meaning, replay)? history.change_intent_required
                • YES → History with business intent: Event Sourcing
                • NO → Audit trail without intent: System-Versioned History Table, Change Data Capture
    • NO → Current state only - record 'no history' explicitly in the information model: —

Outcomes

Each leaf above names the knowledge objects to evaluate. The tree recommends options; the decision itself is recorded as an architecture decision.

Assumptions

  • The tree produces candidates to evaluate, not decisions. Decisions are recorded as ADRs.

Limitations

  • Does not cover retention and erasure conflicts (Data Lifecycle); does not cover history of reference data code lists.
