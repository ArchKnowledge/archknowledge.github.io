Pattern · Data Modeling

System-Versioned History Table

Let the database automatically keep every prior version of a row, with system-maintained transaction-time periods, in an associated history table.

Draft knowledge. Status proposed, quality draft. Not yet reviewed or approved by a human architect.

Problem

Operational data is updated in place, but users or auditors need to see what the data looked like at a past point in (system) time.

Context

Operational databases where history of recorded state is needed and valid-time corrections are rare or not required.

Forces

  • Applications should not have to write history themselves.
  • History must be tamper-resistant.
  • Current-state queries must remain fast.

Solution

Each row carries a system-maintained period (sys_start, sys_end). On update/delete, the DBMS moves the prior version to a history table. Queries use "as of" syntax to read past states.

Architecture

Current table (period open) ──on update/delete──▶ History table (closed periods)
                  ▲                                       │
                  └──────── FOR SYSTEM_TIME AS OF ─────────┘

Advantages

  • Transparent to applications.
  • Consistent, DBMS-enforced transaction time.
  • Standardized in SQL (SQL Standard Temporal Support).

Disadvantages

  • Captures transaction time only; backdated business corrections are not represented as such.
  • History growth needs retention management.

Risks

  • Mistaking system time for business validity leads to wrong reconstructions.
  • Schema changes on temporal tables can be constrained by the DBMS.

When to Use

  • "What did the database say at time T?" is the key question.

When Not to Use

  • Retroactive valid-time corrections must be reconstructable → Bitemporal Data Model.

Alternatives

Bitemporal Data Model, Event Sourcing, application-maintained audit tables.

Examples

  • Reconstructing a customer's contact details as stored at the moment a letter was sent.
