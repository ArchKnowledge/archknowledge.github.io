Governed Analytical Data Platform

Reference architecture for an analytical data platform with layered refinement, embedded quality gates, metadata and lineage, and governance built in.

Draft knowledge. Status proposed, quality draft. Not yet reviewed or approved by a human architect.

Purpose

Provide a reusable structure for analytical platforms that serve trusted, governed data to BI, analytics and data science.

Scope

Ingestion to consumption for analytical use. Excludes operational (OLTP) systems and ML model serving.

Context

Multiple sources, multiple consumers, regulatory reporting, need for history.

Architecture

Sources ─(CDC / batch / events)─▶ RAW ─[DQ gate]─▶ CONFORMED ─[DQ gate]─▶ CONSUMPTION ─▶ BI / analytics / APIs
                                   │                  │                      │
                                   └──── metadata & lineage harvesting ──────┴──▶ Catalog
                                                  governance: contracts, ownership, classification

Components

Component Responsibility Pattern
Ingestion acquire data with lineage Change Data Capture, Batch Extract-Transform-Load
Raw layer immutable landing, replay Layered Data Refinement
Conformed layer cleansed, integrated, historized, concept-linked Bitemporal Data Model or Slowly Changing Dimension Type 2, Concept-to-Model Traceability
Consumption layer purpose-built models dimensional marts
Quality rule evaluation at promotion Data Quality Gate
Metadata & catalog technical, business, lineage metadata Metadata Harvesting, Metadata Management Reference Architecture Architect
Security classification-driven access Security Classification Control Professional

Interfaces

  • Producer interfaces governed by data contracts.
  • Consumer interfaces: SQL, semantic/BI layer, APIs.
  • Metadata API to the catalog.

Data Flows

Source → raw (as received) → conformed (integrated + history) → consumption (fit for use). Issues flow back to source owners.

Governance

Owners per data product/layer; contracts at ingestion; quality rules owned by producers (Quality Is Managed at the Source); decisions recorded as ADRs.

Security

Classification per data set; masking/pseudonymisation in conformed layer for personal data; least-privilege access.

Operational Considerations

Orchestration, observability (freshness, volume, quality), cost management, reprocessing from raw.

Variants

Warehouse-centric; lakehouse (e.g. Apache Iceberg tables); virtualized consumption (Data Virtualization).

Trade-offs

Trust and replayability vs. latency, duplication and cost.

Implementation Considerations

Start with one domain end-to-end including metadata and quality, rather than all sources raw-only.
