Governance

The knowledge itself is governed

Every object moves through a lifecycle. Automated rules check it; people review and approve it. Generation is not approval.

Approval is a record, not a field

Changing status: approved approves nothing. An object counts as approved only when an append-only governance record establishes that transition for its exact version. The record holds one decision for every governance level the object's layers require, each taken by someone with decision rights for that level who is neither the proposer nor the owner.

The validator rejects any approved object without such a record; the pull-request check requires the record to arrive in the same change. 0 objects are approved today — none has been through human review yet.

What the audit trail answers

  • Who proposed the change, and what changed — pull request and Git history
  • Which validation rules ran, with which results — validation report attached to every check run
  • Who reviewed and who approved, per governance level — governance record
  • What was decided, when it was published, what it superseded — record, release tag, supersedes relationships

Human governance and AI assistance

AI is used to draft, classify, link and validate knowledge. It has no decision rights.

AI may

  • discover and extract knowledge
  • propose new objects (status at most proposed)
  • classify and link objects
  • run validation

Only people may

  • review, validate and approve knowledge
  • take architecture and governance decisions
  • mark knowledge as authoritative
  • decide on commercial IP and publication

Decision rights by layer

Meaning is decided before representation, and representation before implementation. A lower level may not silently override a higher one.

  1. Semantic governancedefines meaning
  2. Information model governancedefines representation in an information model
  3. Data architecture governancedefines architectural realization
  4. Technical / formal governancedefines implementation

Automated validation

Every change is checked by 76 rules before it can be merged. Results are valid, warning or blocking error. Examples of blocking errors:

  • an object without an ID, or with a duplicate ID
  • missing required metadata
  • a relationship to an object that does not exist
  • an approved object without an owner
  • a lifecycle transition that skips review
  • a changed ID — IDs are immutable
